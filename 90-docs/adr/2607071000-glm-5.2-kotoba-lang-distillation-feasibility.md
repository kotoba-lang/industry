# ADR-2607071000: GLM-5.2 kotoba-lang specialization — compression feasibility research, Stage 0 validation, and Modal serving economics

## Status

Accepted

## Context

Goal: a kotoba-lang/clj-specialized coding model, ideally small enough to run locally on the murakumo M4 fleet (stretch target: fit on a single 16GB Apple M4 node), that preserves GLM-5.2-class agentic coding capability for kotoba-lang-specific tasks.

Two candidate routes were considered:

- **Route A — compress GLM-5.2 itself**: REAP-style expert pruning calibrated to kotoba-lang/edn/cljc, optionally followed by LoRA/SFT recovery fine-tuning, then quantize for deployment.
- **Route B — distill into an already-small model**: keep domain knowledge in RAG over the kotoba-lang corpus, and specialize a properly-small model (e.g. Qwen3.6-35B-A3B, 3B active) via SFT/LoRA on GLM-5.2-generated agentic trajectories.

This ADR records the research/experimentation that decided between them.

## Decision

### 1. Stage 0 experiment empirically validated Route B

Built a 3-task kotoba-lang benchmark with execution-based scoring (real `clojure -M:test`, scoped to the relevant test namespace, answer file excluded from the RAG index to prevent leakage):

- T1: `kotoba.kgraph/assert-entity` + `assert-entities` (orgs/kotoba-lang/kotoba)
- T2: `kotoba.did-adapter/resolve-did` + `publish-did-key` (orgs/kotoba-lang/kotoba)
- T3: `kotoba.lang.capability-cacao/parse-cap-uri` (orgs/kotoba-lang/kotoba-lang)

Results:

| Task | GLM-5.2 raw (no RAG) | Qwen3.6-35B-A3B (no RAG) | Qwen3.6-35B-A3B + BM25 RAG |
|---|---|---|---|
| T1 kgraph | FAIL (`dc/entity->datoms` hallucinated) | FAIL (same hallucinated fn) | **PASS** |
| T2 did-adapter | FAIL (`did/resolve` hallucinated) | FAIL (same hallucinated fn) | **PASS** |
| T3 capability-cacao | FAIL (`rest` var shadowing → runtime error) | FAIL (unbalanced parens, syntax error) | FAIL but 36/39 assertions pass (only an edge-case bug) |

A ~35B-A3B (3B active) local model with simple BM25 RAG beat the raw 744B/40B-active GLM-5.2 teacher, and the failure mode without RAG was **identical** between the giant teacher and the small model (same hallucinated API names) — direct evidence that the gap is domain knowledge, not general capability, and that RAG closes it.

### 2. Route A's theoretical ceiling falls far short of the 16GB target

GLM-5.2's non-expert backbone (attention + embedding + dense layers + shared expert) is ≈20–25B params and cannot be pruned away regardless of domain. Domain-calibrated "safe zone" expert pruning (65–75% removal, before the reasoning-collapse cliff) lands at ≈200–280B total params — ≈100–140GB even at 4-bit. Reaching 16GB requires removing essentially 100% of routed experts, i.e. deleting nearly all of GLM-5.2's learned capability. Verified against the real `nvidia/GLM-5.2-NVFP4` checkpoint (753B/40B-active, 465GB measured) as the concrete baseline.

### 3. Hardware reality closes Route A off entirely, independent of pruning level

- murakumo fleet: 11× Mac mini M4 16GiB + 1× M1 Max 32GiB operator (no node >32GB exists; confirmed with the user, no undocumented Mac Studio/Ultra).
- `mlx_lm.lora` (and MLX's distributed primitives generally) require the full base model in **one process's** unified memory — no software in murakumo, kotoba-lang, or mlx-lm itself shards one model's weights across nodes for LoRA training.
- Even the most aggressively community-pruned NVFP4 GLM-5.2 checkpoints (e.g. REAP 34–37%-pruned, ~504B/469B) need a **minimum of 6×96GB (576GB) just to hold weights** — confirmed via HF model cards. No single node in the fleet, nor a single NVIDIA B300 (288GB HBM3e, the largest single GPU on the market as of this writing), can hold any real GLM-5.2 derivative.
- murakumo's read-only distributed **inference** path (llama.cpp RPC pipeline-parallel, `mlx-ring`) is unproven even for a fitting-on-paper config: the July 4 benchmark (ADR-2607040845) found the 129.5GiB GGUF Q2_K config never reached a stable first token.

### 4. Modal B200×4 empirical benchmark of the real (unpruned) checkpoint

`nvidia/GLM-5.2-NVFP4` (753B/40B-active, 465GB, official NVIDIA quantization, vLLM/SGLang inference-only) loaded and served correctly via vLLM tensor-parallel-4 on Modal:

- Cold start: 1570–1970s (torch.compile 400–840s is the largest single component; weight load ~150–180s; FlashInfer NVFP4 kernel autotuning ~200–380s; CUDA graph capture ~80s).
- Warm decode throughput: 37–42 tok/s; prefill ≈1,140 tok/s (6,120-token kotoba-lang RAG prompt).
- RAG-augmented output on T1 was correct (passed the real test).
- Cost: ≈$11–14 per cold start at 4×B200 ($25/hr); ≈$0.0375/task once warm. Economically this only works if many tasks are batched into **one long-lived Modal invocation** (load once, loop) — per-task invocations would re-pay the cold-start tax every time.

### 5. Official cold-start mitigations checked and found inapplicable here

- Modal GPU Memory Snapshots (skips torch.compile/kernel-autotune/CUDA-graph-capture by restoring GPU state directly; 9–10x speedups reported by Modal) — **documented as incompatible with multi-GPU code**. Our tensor-parallel-4 setup is disqualified by definition, and no GLM-5.2 derivative fits a single GPU (see §3), so there is no path to single-GPU-izing this workload to use the feature.
- Persisting vLLM's torch.compile cache to a Modal Volume: partial hit only (AOT-compiled artifacts reused; the inductor/dynamo graph cache's key changed between container instances). Cut torch.compile time ~50% (807.65s → 399.95s) but overall cold start only ~18% (1917.8s → 1570.3s), since weight load, kernel autotuning, and CUDA graph capture are not cached and dominate the remainder.

### 6. Decision: pause Route A here, proceed with Route B

Given §2–5, Route A (compress GLM-5.2 itself) cannot reach the 16GB local-fleet target at any pruning level that preserves real capability, and is blocked from cheap cold-start mitigation by the multi-GPU requirement inherent to its size. Route B is both empirically validated (§1) and the only route consistent with local (M4 fleet) deployment. Proceed with Route B: SFT/LoRA-distill Qwen3.6-35B-A3B (or a similarly right-sized model) on GLM-5.2-generated kotoba-lang agentic trajectories, using the Stage 0 harness as the Stage 1/2 starting point.

## Consequences

- (+) The Stage 0 harness (BM25 retrieval over the kotoba-lang/datom-clj/did corpus, 3 execution-verified tasks, `score2.sh` namespace-scoped scoring, `run_model.py`) is directly reusable for Stage 1 (benchmark expansion) and Stage 2 (trajectory generation) against the Route B target.
- (+) No ongoing cloud GPU dependency is required for serving; the M4 fleet remains the deployment target.
- (+) Session compute spend was bounded and mostly diagnostic: OpenRouter GLM-5.2 calls (a few dollars), Modal B200×4 NVFP4 benchmark runs including one GPU-fabric-fault retry (order of $40–50 total). No large irreversible spend was committed.
- (−) The Modal NVFP4 serving harness (`modal_glm52_nvfp4_bench.py`) and the 465GB model + compile-cache Modal Volumes are now a parked artifact — not on the active path unless Route A is revisited.
- (−) The 465GB model Volume + compile-cache Volume remain on Modal (≈433GiB + a few GiB, within the 1TiB/mo free storage tier, ≈$0/mo currently) — should be deleted if not revisited within a reasonable window, or if combined with other account volumes it pushes past the free 1TiB allowance ($0.09/GiB-mo overage).
- (−) The Stage 0 harness itself lives in a session scratchpad (`scratchpad/kotoba-distill-stage0/`, not committed to any repo) — ephemeral; must be rebuilt or deliberately preserved before Stage 1/2 work resumes.
- (−) The diffusion-LM route (LLaDA-8B-Instruct, explored in Stage 0 as a structural-fit check) is deprioritized, not resolved: Modal B200 proved the infra bottleneck fixable (6,700-token RAG prompt ran in 47s vs. the local Mac's 20+min timeout), but zero-shot output quality was poor as expected (untrained), and whether diffusion-LM distillation would out-perform the Route B autoregressive path is still open.

## Alternatives Considered

- **Full GLM-5.2 expert pruning + LoRA recovery on Modal B200/H200 multi-GPU** — rejected. Estimated $150–600 for the training/pruning phase alone (on top of trajectory-generation cost shared with Route B), does not reach the 16GB target even in the best case (§2), and no local hardware exists to do the LoRA step without ongoing cloud dependency (§3).
- **Deploy a Blackwell-cloud-hosted NVFP4 GLM-5.2 derivative instead of the local fleet** — rejected. Contradicts the explicit "local, ideally 16GB" requirement; also still blocked by the 6×96GB-minimum weight-holding floor for any real derivative (§3).
- **LLaDA-8B diffusion distillation as the Route B target instead of Qwen3.6-35B-A3B** — not rejected, deprioritized. Infra-feasible per the Modal B200 result, but needs its own Stage 2-equivalent validation before it can be compared to the AR route on the same footing.
