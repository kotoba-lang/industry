# ADR-2607071600: net-babiniku 完成系 — service completion design (LP, live avatars, murakumo LLM, kisekae editor)

## Status
Proposed (design accepted by user direction 2026-07-07 "do it"; individual milestones land as their own PRs against this map)

## Context

User direction (2026-07-07): "babiniku.net の lp なども含めて、サービスとして完成系を設計して、
また vrm character editor なども kotoba-lang として、ユーザーが使いやすいものを再設計して.
kotoba wasm, cljc, kotobase datomic" — design the *finished* service, LP included, plus a
user-friendly VRM character editor as a kotoba-lang library (that editor is ADR-2607071610,
`kotoba-lang/kisekae`; this ADR is the service that consumes it). Two earlier same-session
directives fold in: "anthropic key はつかわずに murakumo.cloud を使って" (drop the direct
Anthropic key, use murakumo.cloud), and the observation that the deployed page shows "単なる
四角いオブジェクト" (just a box) where an avatar should be.

### Where the product actually stands (Milestones 0–3, all deployed)

The containment architecture is real and tested (`babiniku.governor` HARD/SOFT gate +
escalation, `babiniku.monetization` honest-default HARD-hold, `babiniku.embodiment`
Otete-only gate, 65 nbb checks) and a real chat pipeline exists end-to-end (persona system
prompts, structured-output schema, per-character transcripts, conversation history, thinking
indicator — PRs #15–#21). But as a *service* it is incomplete in exactly four ways:

1. **No live LLM** — `ANTHROPIC_API_KEY` was never provisioned; every chat returns the
   honest 503. Now superseded by the murakumo direction anyway.
2. **No avatars** — the render canvas shows a placeholder box unless a visitor hand-types
   a `?vrm=` URL param. Characters have no visual identity.
3. **No character creation** — the roster is 4 hardcoded personas; there is no path for a
   user to make their own character, which is also the missing supply side of
   ADR-2607062200's creator-economy model (80/20 split needs creators).
4. **The page reads as an engineering dashboard** — hero copy exists (PR #19), but the
   dominant content is milestone status text and four audit ledgers.

### Research grounding (verified this session)

- **murakumo has two distinct live endpoints.** `api.murakumo.cloud/v1/messages`
  (`local-murakumo`) is an Anthropic-Messages-API-shaped bridge to the *self-hosted*
  `qwen-agentworld-35b-a3b` on the physical fleet (ADR-2607051431) — verified to never
  touch an `ANTHROPIC_API_KEY`; caller auth is `ANTHROPIC_PROXY_TOKEN` (a murakumo-side
  Worker secret; auth is a no-op if unset). `murakumo.cloud/api/v1/messages`
  (`cloud-murakumo`/"Sora") is a *generic configurable reverse proxy* whose production
  upstream is not verifiable from the repo. Precedent caller: `local-manimani`
  (`manimani.kotodama-backend` via `langchain.model/anthropic-model` — standard Messages
  JSON body, `x-api-key`/`anthropic-version` headers, nilable key).
- **The avatar gap is plumbing, not architecture.** `network-isekai`'s `isekai.stage`
  already runs the exact multi-avatar pattern needed (`avatar-cache` atom keyed by URL,
  idempotent `ensure-avatar!`, per-frame draw of `:ready` entries); `babiniku.web` has the
  single-shot MVP version of the same stack. Porting is ~40 lines plus a
  register-callback indirection `babiniku.broadcast` already models.
- **License-clear sample VRMs are scarce.** The VRM Consortium sample repo yields exactly
  2 practical avatar models (Seed-san — already used — and VRM1_Constraint_Twist_Sample,
  10.7 MB, both VRM Public License 1.0 / pixiv). Four distinct hardcoded avatars cannot be
  sourced from it.
- **The editor engine already exists** — `org-vrmc-vrm`'s restored
  decompose/compose/export pipeline (ADR-2607071610 has the full inventory).

## Decision

### 1. 完成系 defined — five capabilities, each with a "done" criterion

| # | Capability | Done when |
|---|---|---|
| C1 | **Live chat** | A visitor sends a message and receives an in-character reply generated by murakumo's self-hosted model, gated by `review-turn`, in production |
| C2 | **Live avatars** | Each roster character card shows/selects its own rendered VRM (no `?vrm=` param, no placeholder box as the default face of the product) |
| C3 | **Character creation** | A visitor assembles a character in the kisekae flow, it persists (kotobase), and its avatar + persona join their roster and are chattable |
| C4 | **Visitor-shaped LP** | First screen is product (hero → live character gallery → create-your-own entry → tiers), with containment transparency as a labeled trust section, not the page's dominant voice |
| C5 | **Monetization** | UNCHANGED: honest HARD-hold until the etzhayyim rail matures (ADR-2607071000). The LP shows tiers as 準備中 — completion of *this* ADR does not require live payments |

### 2. LLM backend: murakumo, `api.murakumo.cloud` (supersedes ADR-2607070800's model choice in part)

- `functions/api/chat.js` retargets `https://api.murakumo.cloud/v1/messages`. The endpoint
  is Anthropic-Messages-shaped, so the request construction survives; `MODEL` becomes the
  fleet model id and the `@anthropic-ai/sdk` client gets `baseURL` pointed at the bridge.
  **`murakumo.cloud/api/v1/messages` (Sora proxy) is explicitly rejected as the target**:
  its upstream is operator-configurable and unverifiable — it *could* be pointed at real
  Anthropic, which would silently violate the user's "anthropic key はつかわずに" intent.
- Auth: a `MURAKUMO_PROXY_TOKEN` Cloudflare Pages secret, sent as the bridge's expected
  token **iff the bridge's `ANTHROPIC_PROXY_TOKEN` is set** (open item: its production
  state is unknown; if unset, auth is a no-op and chat works with zero secrets). Either
  way the honest-default 503 pattern stays: unprovisioned/unreachable upstream must never
  fabricate a reply.
- **Structured outputs are unverified on the bridge.** ADR-2607070800's design leaned on
  `output_config.format`; a Messages-*shaped* bridge to a qwen model may ignore it.
  Design: keep sending the schema (harmless if ignored), add an explicit
  produce-only-this-JSON instruction to the system prompt, parse defensively, and rely on
  the unchanged `review-turn` gate — a malformed emotion/motion-cue already HARD-holds,
  and the transcript already renders holds honestly. Verification is the first live call
  after retargeting; if the model can't hold the JSON contract acceptably, the fallback
  (decided then, not now) is a murakumo-side response-shaping layer, not a client hack.
- ADR-2607070800 is superseded **only** in provider/model choice; everything else it
  decided (server-side call boundary, persona system prompts, schema-mirrors-governor
  vocabulary, honest-default, no self-fine-tune *in babiniku itself*) carries forward.

### 3. Per-character live avatars

- `babiniku.character/roster` gains `:vrm-url` per character.
- `babiniku.web` ports `isekai.stage`'s `avatar-cache`/`ensure-avatar!` (keyed by URL,
  `:loading/:ready/:error`), exposes `select-avatar!` through the same register-callback
  indirection `babiniku.broadcast` uses, and the draw loop renders the selected
  character's `:ready` parts (placeholder box only while nothing is ready).
- UI: selecting a character (clicking its card / focusing its chat input) dispatches the
  avatar swap. GPU-buffer disposal for swapped-out avatars is explicitly deferred
  (network-isekai's own precedent) — low-frequency swaps, acceptable leak, follow-up.
- **Avatar content**: Seed-san + VRM1_Constraint_Twist_Sample cover 2 slots today; the
  other 2 characters share a placeholder until kisekae-produced avatars fill them. That
  scarcity is *why C3 matters*: user-created avatars are the durable, license-clean
  supply (the creator sets the meta/license at export — `kisekae.build/apply-meta`).

### 4. Character creation via kisekae (ADR-2607071610)

- babiniku embeds the kisekae flow ("Create your character"): pick base → swap parts →
  recolor → name/license → save. The flow's UI composes `kotoba-lang/canvaskit`
  (viewport), `kami-webgpu` (live preview through the same avatar-cache), and
  `kotoba-lang/editor` (walk-the-spec controls) around the kisekae domain library.
- Persistence: character specs via `kisekae.store`'s contract — `MemSpecStore` (browser
  session) first, kotobase-backed store as the follow-up wiring, with user identity via
  the actor-key CACAO self-mint convention (`manifest/repos.edn` `:kotoba`) when accounts
  arrive. The spec (small EDN) is the artifact; the `.vrm` is derived — this is the
  kotobase-datomic story the user's directive names.
- Created characters register into the visitor's roster with a default persona template
  (bio/speech-examples editable — text fields on the same spec), making them chattable
  through the identical governor-gated pipeline. Creator-economy hook: a created
  character is a creator asset; when the etzhayyim rail matures, ADR-2607062200's 80/20
  applies to it with no new design.

### 5. LP structure (C4)

Order: hero (exists) → **character gallery** (live avatar + tagline + "chat" per
character; the render canvas becomes the gallery's stage rather than a dead half-page) →
**"Create your character"** entry → **tiers** (準備中, honest) → **"How containment
works"** — the ledgers/pending-escalation panels moved under a labeled trust section with
one paragraph of framing. Nothing is deleted: containment transparency is a deliberate,
repeatedly-reaffirmed design choice; this re-frames it as the differentiator it is instead
of the landing experience.

### 6. Out of scope, unchanged

Monetization capability (HARD-held, ADR-2607071000), the NSFW-tier decision
(ADR-2607062200 #5), shinshi.club (other agent), giemon embodiment scope (ADR-2607062210),
and `babiniku.net` DNS (still blocked on a dashboard action or DNS-scoped token).

## Consequences

- Implementation order (each its own PR series): **M4** murakumo chat live (retarget +
  secret decision + first live verification incl. the structured-output question) → **M5**
  avatars (roster `:vrm-url` + stage port) → **M6** kisekae flow embed (MemSpecStore first,
  kotobase follow-up) → **M7** LP restructure. M4 and M5 are independent and can land in
  either order.
- Open items carried: murakumo bridge's `ANTHROPIC_PROXY_TOKEN` production state; the
  qwen model's JSON-contract fidelity; 2 missing character avatars until kisekae supplies
  them; kotobase-backed SpecStore + account identity.
- `net-babiniku` gains dependencies on `kotoba-lang/kisekae`, `canvaskit`, and
  `kotoba-lang/editor` when M6 lands (all sibling `:local/root`, the existing convention).
- ADR-2607070800 amended in place (provider superseded, boundary design retained).

### Addendum (2026-07-08): "2 missing character avatars" closed — Rin and Mei get
real composed avatars, plus a real VRM license-credit compliance gap fixed

M6's compose engine (ADR-2607071610, shipped and verified live) closes this open
item without any new third-party asset: Rin and Mei now get real avatars **composed
from the same two already-licensed VRM Consortium sample files** Aoi/Yui already
use (`jk-luxury/net-babiniku#39`) — Rin = VRM1_Constraint_Twist_Sample's body with
Seed-san's hair+outfit; Mei = Seed-san's body/outfit with VRM1_Constraint_Twist_
Sample's hair+face (Twist-Sample has no separate `:outfit` category to donate).

**License basis checked directly against both files' embedded `VRMC_vrm.meta`, not
assumed**: both declare `modification: "allowModificationRedistribution"`,
`avatarPermission: "everyone"`, `allowRedistribution: true` under VRM Public
License 1.0 — composing/remixing parts between them is explicitly within license
terms. This also surfaced a real, previously-missing compliance gap: Seed-san's
`creditNotation` is `"required"` (credit VirtualCast, Inc.), but nothing in the app
credited it anywhere for Aoi's existing avatar either. Every built-in character now
carries `:avatar-credit`, rendered unconditionally and visibly on its card.

A new `:avatar-spec` field (built-in characters only, distinct from user-created
characters' `:kisekae/spec`) keeps `character-card-view`'s `created?` check
correctly scoped — Rin/Mei get real composed avatars without gaining the
Edit/Export/Delete UI meant only for what a visitor actually created. Verified live
in production: both avatars render as full, correctly-posed, distinct humanoids;
no console errors; `nbb character`/`governor`/`monetization`/`embodiment`/`persona`
all pass.

Remaining open items unchanged: `MURAKUMO_PROXY_TOKEN` production state, `babiniku.net`
DNS, kotobase-backed SpecStore + account identity.

## Alternatives Considered

1. **Keep the direct Anthropic backend and just provision the key.** Rejected — explicit
   user direction; also the key was never provisioned in three weeks of asking, while
   murakumo is first-party infrastructure.
2. **Target `murakumo.cloud/api/v1/messages` (Sora proxy) since the user's words name that
   domain.** Rejected as *primary* — its upstream is unverifiable from the repo and could
   be real Anthropic, silently defeating the directive's intent; `api.murakumo.cloud` is
   the verified self-hosted path. Recorded so the choice is reviewable.
3. **Buy/commission 4 avatar files instead of building creation.** Rejected as the
   *systemic* answer — it fixes 4 slots once, leaves user-generated characters (the
   creator-economy supply) unsolved, and re-imports license risk kisekae's meta stamping
   avoids.
4. **Strip the audit ledgers off the page for a "clean" LP.** Rejected — containment
   transparency is a standing product decision (ADRs 2607062200/0001); re-framed and
   repositioned instead.
5. **Wait for accounts/auth before any character creation.** Rejected — MemSpecStore
   gives a real, honest single-session creation experience now; kotobase persistence is
   additive wiring behind an already-tested contract.
