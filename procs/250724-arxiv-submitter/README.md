### プロジェクト「ACJ - yamato-ll1」取り組みのまとめ

#### 1. プロジェクトの目的

このプロジェクトの目的は、**日本語の特定のサブセット（断片）を解析するためのLL(1)再帰下降パーサーをGo言語で実装し、その成果を学術論文としてarXivに投稿すること**でした。

*   **ACJ (Attempto Controlled Japanese)**: 論文執筆の過程で定義した、私たちが解析対象とする「制御された日本語」の名称です。曖昧さがなく、機械が処理しやすいように語彙や文法が厳密に定義されています。
*   **yamato-ll1**: 上記のACJを解析するために私たちが実装したGo製パーサーの、このリポジトリにおける名称です。

#### 2. 開発フェーズ (Step by Step)

##### ステップ1: 文法設計と古典日本語パーサーの実装

最初に、比較的シンプルな「古典日本語（大和言葉）」の文法を対象としました。

*   **LL(1)文法の設計 (`README.md`)**:
    *   基本となる文法を定義し、パーサーで扱えるように「左再帰の除去」や「左ファクタリング」といった変換を行い、LL(1)文法を確定させました。この文法定義がパーサー全体の設計図となります。
*   **字句解析器 (Lexer) の実装 (`internal/lexer`)**:
    *   入力された日本語の文字列を、意味のある最小単位「トークン」（例：名詞、助詞、動詞）に分割するプログラムです。
    *   日本語（マルチバイト文字）を正しく扱うため、Goの`rune`型を使い、1文字ずつ読み進める初期実装を行いました。
*   **抽象構文木 (AST) の定義 (`internal/ast`)**:
    *   パーサーが解析した文の構造を表現するためのデータ構造です。例えば、「文」は複数の「節」から成り、「節」は「名詞句(NP)」と「動詞句(VP)」から成る、といった階層構造をGoの`struct`で定義しました。
    *   デバッグしやすいように、ASTを文字列として出力する`String()`メソッドを各ノードに実装しました。
*   **構文解析器 (Parser) の実装 (`internal/parser`)**:
    *   Lexerが生成したトークンの流れを読み込み、文法規則に従ってASTを組み立てる、このプロジェクトの中核部分です。
    *   文法規則の一つ一つに対応する`parse...()`という関数を作成し、関数がお互いを再帰的に呼び出す「再帰下降」という手法で実装しました。

##### ステップ2: 現代日本語への拡張とリファクタリング

次に、パーサーをより実用的な「現代日本語」に対応させる拡張を行いました。

*   **新要件**: 助詞「は」「の」、丁寧形「ます」「です」、過去形「た」を追加。
*   **文法とASTの拡張**:
    *   新しい単語（助詞、助動詞）に対応するため、`token.go`に定義を追加しました。
    *   最も大きな変更はASTで、「〜です」という文（コピュラ文）と、「〜ます」という文（動詞文）の構造的な違いを吸収するため、`VP` (動詞句) の定義を大きく変更し、`CopulaPhrase`と`VerbPhrase`という新しいノードを導入しました。
*   **パーサーの拡張**:
    *   `parseVP`関数が、次に来るトークンを「先読み」することで、コピュラ文か動詞文かを判断し、それぞれ別の解析処理に分岐するようにロジックを修正しました。
*   **Lexerの全面リファクタリング**:
    *   当初の1文字ずつ読み込むLexerは、日本語の単語の区切り判定が複雑で、バグが発生しがちでした。
    *   そこで方針を転換し、Goの標準ライブラリ`bufio.Scanner`を`bufio.ScanWords`で使うことで、**単語分割処理を標準ライブラリに任せる**ようにしました。これにより、コードが劇的にシンプルになり、安定性も向上しました。**（教訓：車輪の再発明を避け、標準ライブラリをうまく活用することの重要性）**

#### 3. 論文執筆とarXiv投稿フェーズ

実装の成果を論文にまとめ、国際的な論文リポジトリであるarXivへの投稿を目指しました。ここでも多くの技術的な問題に直面しました。

*   **論文の執筆と再構成 (`paper.tex`)**:
    *   当初の論文を、より学術的な体裁にするため、先行研究である「Attempto Controlled English (ACE)」のスタイルを参考に全面改稿しました。ここで言語仕様を「ACJ」と名付けました。
*   **LaTeX環境の構築とトラブルシューティング**:
    1.  **問題**: 日本語を含む`.tex`ファイルをPDFにコンパイルする`xelatex`コマンドが存在しませんでした。
    2.  **解決策**: `brew install --cask mactex`でLaTeX環境をインストールしました。しかし、パスが通らない問題が頻発し、シェルのパス更新(`eval path_helper`)やMacTeXの再インストールを経て、ようやくコマンドが使えるようになりました。
    3.  **問題**: いざコンパイルすると、日本語フォントが見つからない、太字にできない等のエラーが多発しました。
    4.  **解決策**: PCにインストールされていないフォント（Takao PMincho）の指定をやめ、macOS標準の「ヒラギノ明朝」を指定することで解決しました。
*   **arXiv投稿プロセスのデバッグ**:
    1.  **問題**: arXivに`.tar.gz`をアップロードすると、「処理済みのPDFが含まれている」というエラーでリジェクトされました。
    2.  **解決策**: ローカルで生成された`.pdf`や`.log`ファイルを含めず、`.tex`ソースファイル**だけ**をアーカイブし直すことで解決しました。**（教訓：投稿システムの要求を正確に理解すること）**
    3.  **問題**: 再投稿すると、今度はarXivのサーバー上でコンパイルが失敗しました。ログを分析すると、arXivがデフォルトの`pdflatex`を使おうとして、日本語パッケージ(`zxjatype`)がエラーを出していることが判明しました。
    4.  **解決策**: arXivのUIには`xelatex`の選択肢がありませんでした。そこで、`.tex`ファイルの1行目に`%!TEX program = xelatex`という「マジックコメント」を追記し、コンパイラを強制指定する方法を試しましたが、これも通りませんでした。
    5.  **最終解決策**: `xelatex`に依存するのをやめ、**arXivの標準環境である`pdflatex`で日本語を扱える`CJKutf8`パッケージを使う**ように、`.tex`ファイルを根本的に書き直しました。これにより、無事にarXivでのコンパイルが通るようになりました。**（教訓：開発環境と本番環境（ここではarXiv）の違いを認識し、本番環境の制約に合わせて実装を調整することの重要性）**

#### 4. まとめと現状

現在、ACJという制御日本語の仕様を定義し、それを解析するパーサー`yamato-ll1`をGoで実装。そして、その成果をまとめた論文のソースコード(`paper.tex`)が、arXivのシステムで正しくコンパイルできる状態になっています。

後輩の皆さんには、このサマリーとリポジトリ内のコード、そして`README.md`や`paper.tex`を読むことで、プロジェクトの全体像を掴んでいただければと思います。特にトラブルシューティングの過程は、実践的な問題解決の良いケーススタディになるはずです。
