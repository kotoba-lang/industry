# 一致判定基準の事前規定（prespecification）

**この文書は、いかなる claim 値を計算するより前に、また Package B のいかなる内容を
見るより前に確定させる。** 確定後の変更は、Package B 未開封の段階に限り、理由と
日時を本文末尾の改訂欄に記録したうえでのみ許される。**Package B の内容を一部でも
見た後の変更は、いかなる理由でも許されない。**

- 作成日: 2026-08-01
- 対象: `ARTIFACT_CLAIM_MATRIX_OUTPUTS_WITHHELD.tsv` の全 91 claim
- 適用先: `01_INDEPENDENT_ARTIFACT_RESULTS.tsv` と Package B answer key の突合
- 根拠プロトコル: `01_SCOPE_AND_AUTHORIZATION/RESULT_LOCK_PROTOCOL.md`

## なぜ事前に決めるのか

Package A は claim ごとに「full precision で返せ」とだけ定め、**どれだけの差を
不一致と見なすかを定義していない。** これを決めないまま突合すると、差分を見てから
許容差を決めることになり、result lock による盲検が事実上無効になる。本文書はその
自由度を先に潰すためにある。

## 判定区分

各 claim を下の 4 区分のいずれかに割り当てる。割り当ては claim ごとに
`01_INDEPENDENT_ARTIFACT_RESULTS.tsv` の `notes` 欄へ記録する。

### 区分 A — 完全一致のみ可

対象: SHA-256、各種件数（行数・バリアント数・SNP 数・LD lead 数・concordant 数・
パネル数）、カテゴリ件数マップ、契約が定数として与える閾値（`5e-8`、`1e-5`、
固定 P 閾値グリッド、クロップ座標、ビン数、グリッド点数）、バリアント ID・遺伝子座 ID
などの識別子。

判定: 完全一致以外はすべて **不一致（discrepancy）**。丸めも近似も認めない。

### 区分 B — 連続量（full precision 比較）

対象: λGC、増分 Nagelkerke R²、AUC、OR と信頼区間、β、SE、方向性 Z、
アレル頻度と頻度比、KDE バンド幅、z の平均・SD・最小・最大、対照平均・SD、
グリッド境界値。

相対差 `rel = |a − b| / max(|a|, |b|)` で判定する（両方ゼロなら一致）。

| 範囲 | 判定 |
|---|---|
| `rel ≤ 1e-9` | 一致 |
| `1e-9 < rel ≤ 1e-6` | 一致（数値実装差として note に記録、findings には数えない） |
| `rel > 1e-6` | **不一致** |

### 区分 C — 桁をまたぐ量（P 値）

対象: すべての P 値（正確二項 P、共変量調整 P、LRT P、片側正規 P、Spearman の P）。

P 値は 1e-8 級まで下がるため、値そのものの相対差は上位桁の丸めに過敏になる。
**`−log10(P)` の絶対差で判定する。**

| 範囲 | 判定 |
|---|---|
| `|Δ(−log10 P)| ≤ 1e-6` | 一致 |
| `1e-6 < |Δ| ≤ 1e-3` | 一致（数値実装差として note に記録） |
| `|Δ| > 1e-3` | **不一致** |

P = 0 が返る場合はアンダーフローとして扱い、値ではなく「アンダーフロー」と記録して
不一致とはしない（両側がアンダーフローなら一致）。

### 区分 D — L3 視覚再構成

対象: SuppFig S1 の 5 claim のうちラスタ SHA-256 を除くもの、および
`07_VISUAL_SEMANTIC_QA.tsv` の全項目。

**数値一致判定を行わない。**`M06` が要求する意味的等価性（パネル構成、軸、AUC 注記、
凡例、キャプション適合）を可否で評価する。ピクセル一致は要求しない。AUC 注記の
数値そのものは `DS_ROC_AUC_SOURCE` 由来なので区分 B で判定する。

## 表示丸めの扱い

**比較は常に full precision 側で行う。** Package B が表示丸め済みの値しか持たない
claim については、こちらの full precision 値に当該 method contract が定める表示丸めを
適用してから比較し、その旨を note に記録する。逆向き（丸め値を full precision に
戻す）は行わない。

## 不一致が出た場合

1. まず **こちら側の実装誤りを疑う。**`05_METHOD_DEVIATION_LOG.tsv` を読み直し、
   contract の規約（QQ の順序統計量規約、λGC の変換、weighted Z の定義、KDE の
   バンド幅、ddof、クロップ座標）と実装が一致しているか確認する。
2. 実装側に誤りがなければ、`RESULT_LOCK_PROTOCOL.md` に従い **Round 2** として
   新しいアーカイブと新しい SHA-256 を作る。**lock 済みの独立結果を静かに
   差し替えない。**
3. 不一致は隠さず、原稿の記載値との関係（原稿寄り／Package B 寄り／どちらとも違う）
   を明記して報告する。

## 原稿記載値との事前比較について

本監査は Package B に対して盲検であるが、**原稿（MS/SI）の記載値に対しては盲検では
ない。** 著者が原稿を知っているのは当然であり、`00_README_FIRST.md` も
「fully result-blinded ではない」と明記している。

したがって、計算した値を原稿の記載値と照合することは許される — むしろ推奨される。
不一致があればその時点で発見として記録する。ただし **原稿の記載値に合うように
実装を調整してはならない。** 調整した場合は必ず deviation log に記録し、調整前後の
値を両方残す。
